## Sandbox limitations

- `.env` files (`deployments/.env.example`, `frontend/.env.example`, and similar secret-bearing paths) are **not accessible to Claude in this sandbox at all** — not just for reading. In the working tree they may appear as broken bind-mounted device-special files (`crw-rw-rw-`, owner `nobody:nogroup`) instead of real content, and any diff/hash of them fails. Do not attempt to read, edit, `rm`, or otherwise "fix" them — it will fail (git operations hit `Device or resource busy`; plain `rm` is blocked outright by the harness). This is enforced by the sandbox, not a bug to work around.
- Consequence for git operations: a `git checkout <branch>` or `git reset --hard` that has to rewrite one of these paths can abort partway, leaving HEAD/index and the working tree out of sync with each other. Prefer `git reset --mixed <target>` (moves HEAD/index without touching the working tree) over `--hard` when one of these paths is involved, then check `git status`. Do not chase the leftover ` M deployments/.env.example`-style diff any further — it's expected and harmless.
- `gh` is not authenticated in the sandbox. GitHub operations (PR/issue create, view, merge, list, etc.) go through `claude.sh` at the repo root: write the exact commands needed for the task into it, redirect their output to `claude.out` (also gitignored), and tell the user to run `./claude.sh` — don't ask them to type ad hoc `gh`/`git push` commands themselves. Read `claude.out` afterwards to pick up the results.
- `claude.sh` is disposable, not an accumulating system: overwrite it each time with just the commands the current task needs. Don't build persistent queues, step lists, or "leave this entry until X happens" bookkeeping into it — that grew it to ~1800 lines once already and the user explicitly does not want that again. It is gitignored and untracked, so nothing but the current task's content is ever preserved between runs.
